# In-app update research for Peacock Notes

Research date: 2026-09-17

## Verdict

Yes. Peacock Notes can check GitHub Releases for a newer APK, download it, and open the system package installer without root. Two limits define the feature: the install is never silent, the user must tap through the system installer and must have enabled "Allow app installs" for Peacock Notes at least once, and shipping the feature needs `android.permission.REQUEST_INSTALL_PACKAGES`, a native change that EAS Update cannot deliver. A successful update with the same package, same signing key, and an equal or higher `versionCode` runs in place and preserves SQLite data and files. Treat this as the binary path for native changes and keep EAS Update for JS-only changes, per [docs/ota-updates-research.md](ota-updates-research.md).

## What is possible

- Discover the latest full release with `GET /repos/skychaze/PeacockNotes/releases/latest`. The endpoint returns the most recent non-prerelease, non-draft release sorted by `created_at`, works unauthenticated for public repos, requires a valid `User-Agent` header (missing or invalid gives 403), and counts against 60 requests per hour per IP. [GitHub: get the latest release](https://docs.github.com/en/rest/releases/releases#get-the-latest-release) [GitHub: rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-unauthenticated-users) [GitHub: User-Agent](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api#user-agent)
- The repo is public. The latest release is `v1.1.4` with asset `peacocknotes-v1.1.4-14.apk` (99,431,904 bytes) and a `sha256` digest; asset objects expose `name`, `browser_download_url`, `size`, `content_type`, and `digest`. [live API check](https://api.github.com/repos/skychaze/PeacockNotes/releases/latest) [GitHub: release asset schema](https://docs.github.com/en/rest/releases/assets)
- `browser_download_url` answers with a 302 to a signed `release-assets.githubusercontent.com` URL valid for about an hour (verified from response headers). expo-file-system downloads with OkHttp, whose default is to follow redirects. [OkHttp source](https://github.com/square/okhttp/blob/master/okhttp/src/commonJvmAndroid/kotlin/okhttp3/OkHttpClient.kt)
- The APK must reach the installer as a `content://` URI. expo-file-system already ships `FileSystemFileProvider` with `grantUriPermissions="true"`, and `getContentUriAsync` returns that URI; a `file://` intent to another app throws `FileUriExposedException` for targets N and higher. [installed legacy types](../node_modules/expo-file-system/build/legacy/FileSystem.d.ts) [Android: FileUriExposedException](https://developer.android.com/reference/android/os/FileUriExposedException)
- Launch the installer with `android.intent.action.VIEW`, MIME `application/vnd.android.package-archive`, and flag `1` (`FLAG_GRANT_READ_URI_PERMISSION`). The platform installer registers `InstallStart` for exactly `VIEW` plus `content` scheme plus that MIME type; `ACTION_INSTALL_PACKAGE` also matches but is deprecated since API 29 in favor of `PackageInstaller`, and `EXTRA_NOT_UNKNOWN_SOURCE` belongs to that deprecated path only. [AOSP PackageInstaller manifest](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/PackageInstaller/AndroidManifest.xml) [Android: ACTION_INSTALL_PACKAGE](https://developer.android.com/reference/android/content/Intent#ACTION_INSTALL_PACKAGE) [Android: EXTRA_NOT_UNKNOWN_SOURCE](https://developer.android.com/reference/android/content/Intent#EXTRA_NOT_UNKNOWN_SOURCE) [Expo: FileSystem legacy example](https://docs.expo.dev/versions/v54.0.0/sdk/filesystem/)
- expo-intent-launcher 13.0.8 exposes `MANAGE_UNKNOWN_APP_SOURCES`, and `startActivityAsync` accepts `data`, `type`, `flags`, `extra`, `packageName`, and `className`; when both `data` and `type` are set it calls `setDataAndType`. Opening it with `data: 'package:com.roy.peacocknotes'` goes straight to the per-app "Allow app installs" screen. [installed enum](../node_modules/expo-intent-launcher/src/IntentLauncher.ts) [installed Android module](../node_modules/expo-intent-launcher/android/src/main/java/expo/modules/intentlauncher/IntentLauncherModule.kt) [Android: ACTION_MANAGE_UNKNOWN_APP_SOURCES](https://developer.android.com/reference/android/provider/Settings#ACTION_MANAGE_UNKNOWN_APP_SOURCES)
- The check and the download can run in the app process while the user keeps working, then a prompt asks to install. No foreground service or WorkManager is required for the common case; if the process dies mid-download, restart it.

## What is not possible

- No silent or automatic install. `PackageInstaller` lets any app create a session, but "Committing may require user intervention to complete the installation", and automatic completion is documented only for the device owner or affiliated profile owner. The privileged `INSTALL_PACKAGES` permission is "not for use by third-party applications", and a package installer session reports `STATUS_PENDING_USER_ACTION` when the user must act. [Android: PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller) [Android: INSTALL_PACKAGES](https://developer.android.com/reference/android/Manifest.permission#INSTALL_PACKAGES) [Android: STATUS_PENDING_USER_ACTION](https://developer.android.com/reference/android/content/pm/PackageInstaller#STATUS_PENDING_USER_ACTION)
- No self-relaunch. Android stops the app during install; the user reopens it.
- The app cannot skip the per-source consent. From Android 8.0 the user enables "Allow app installs" for Peacock Notes in the Install unknown apps screen, and a source should check `canRequestPackageInstalls()` first. That method is a platform API that no installed Expo package exposes, so either accept the installer's own dialog or add a tiny native module. [Android: install unknown apps guide](https://developer.android.com/studio/publish#publishing-unknown) [Android: canRequestPackageInstalls](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()) [Android 8.0 changes](https://developer.android.com/about/versions/oreo/android-8.0-changes#security-all)

## Implementation sketch

Version comparison:
- Read the installed identity from `Constants.expoConfig`: the embedded public config for this repo contains `version` 1.1.4 and `android.versionCode` 14 (verified by resolving the public config and by the native `assets/app.config` reader). Compare on `android.versionCode`. `Constants.platform.android` is an empty map in expo-constants 18, and `expo-application` (`nativeBuildVersion`) is not installed. If an OTA update is running, `expoConfig` comes from the update manifest, so keep OTA and binary versions in step. [installed Constants.ts](../node_modules/expo-constants/src/Constants.ts) [installed ConstantsService.kt](../node_modules/expo-constants/android/src/main/java/expo/modules/constants/ConstantsService.kt)
- Parse the remote identity from the release: tag `v1.1.4` and asset `peacocknotes-v{version}-{versionCode}.apk`. The workflow rejects a tag that differs from `expo.version` and builds exactly that asset name, so the versionCode is in the filename. Compare remote code > installed code, never tag recency. [.github/workflows/release.yml](../.github/workflows/release.yml)

Installed packages, used as follows:
- React Native `fetch` for the GitHub API call with `User-Agent` and `Accept: application/vnd.github+json`.
- `expo-file-system/legacy` (already used across `src/`) for `downloadAsync` into `cacheDirectory` and `getContentUriAsync`. These are deprecated and throw if imported from the package root; the new API equivalents are `File.downloadFileAsync` and `File.contentUri`.
- `expo-intent-launcher` for the install intent and the unknown-sources settings screen.
- `expo-constants` for the installed version; `expo-updates` stays as is for JS-only releases.

Config and native changes:
- Add `android.permission.REQUEST_INSTALL_PACKAGES` to `android.permissions` in `app.json`. It is currently neither listed nor blocked there, and the checked-in generated manifest declares no install permission today, so prebuild will add it; the three `blockedPermissions` entries are unaffected. [app.json](../app.json) [AndroidManifest.xml](../android/app/src/main/AndroidManifest.xml)
- No Gradle, FileProvider, or `queries` changes. The app targets API 36 (expo-autolinking builds the `expoLibs` catalog from React Native's catalog, where `targetSdk = "36"`), above the Android 14 and 15 minimum installable targets of 23 and 24. [expo-autolinking settings plugin](../node_modules/expo-modules-autolinking/android/expo-gradle-plugin/expo-autolinking-settings-plugin/src/main/kotlin/expo/modules/plugin/ExpoAutolinkingSettingsExtension.kt) [React Native libs.versions.toml](../node_modules/react-native/gradle/libs.versions.toml) [Android 14](https://developer.android.com/about/versions/14/behavior-changes-all#minimum-target-api-level) [Android 15](https://developer.android.com/about/versions/15/behavior-changes-all#minimum-target-api-level)
- Optional later: a small native function for `canRequestPackageInstalls()` and a streaming SHA-256. No installed package hashes a file with SHA-256, and `expo-crypto` is absent, so the first cut verifies the API `size` and relies on the installer's certificate check.
- Because the permission is native, the feature only reaches users in a new signed binary. Existing installs need one manual install of that binary; EAS Update cannot bootstrap it.

## Limits and risks

- Data safety: an update succeeds only with the same application ID, same signing certificate (or valid rotation), and a `versionCode` greater than or equal to the installed one; otherwise the user must uninstall, which "erases all app data". App-specific files are removed on uninstall, so a successful update preserves SQLite, files, and preferences. [Android: how app updates work](https://developer.android.com/google/play/app-updates) [Android: versionCode and downgrades](https://developer.android.com/studio/publish/versioning#versioningsettings) [Android: signing considerations](https://developer.android.com/studio/publish/app-signing#signing-considerations) [Android: app-specific storage](https://developer.android.com/training/data-storage/app-specific)
- The platform itself refuses a lower `versionCode`, and the in-app check must do the same, including when `releases/latest` points at a lower versionCode.
- Integrity: HTTPS for the API and the download, compare the local file size to the API `size`, optionally verify the API `digest` (`sha256:...`) once a hashing path exists. A tampered APK fails the installer's certificate comparison unless it is signed with the release keystore, which is the real cryptographic gate. [Android: signing considerations](https://developer.android.com/studio/publish/app-signing#signing-considerations)
- Interrupted downloads: legacy `downloadAsync` deletes the destination, streams into it, and resolves with an HTTP `status` even for error responses, so the app must check `status` and `size` and never launch the installer for a partial file; `createDownloadResumable` supports resume. The new `downloadFileAsync` rejects non-2xx but can leave a partial file on Android. [installed legacy source](../node_modules/expo-file-system/android/src/main/java/expo/modules/filesystem/legacy/FileSystemLegacyModule.kt) [installed new API types](../node_modules/expo-file-system/build/ExpoFileSystem.types.d.ts)
- Keep the check low frequency or user-initiated. 60 unauthenticated API calls per hour per IP is ample, a failed check must be silent, and an offline device must never block startup. expo-intent-launcher also permits only one launched activity at a time.
- Platform notes: per-source consent starts at Android 8.0; Android 12 blocks touches that pass through untrusted overlays, which matters only if another app draws one over the installer, since Peacock Notes has SYSTEM_ALERT_WINDOW blocked; Android 14 and 15 raised the minimum installable target SDK to 23 and 24; the Android 16 behavior-changes list adds no install-flow change; Android developer verification applies to sideloads on certified devices with a regional deadline of September 30, 2026 for participating stores in Brazil, Indonesia, Singapore, and Thailand and a global rollout in 2027, so confirm first-install distribution stays workable. [Android 12](https://developer.android.com/about/versions/12/behavior-changes-all#untrusted-touch-events) [Android 14](https://developer.android.com/about/versions/14/behavior-changes-all#minimum-target-api-level) [Android 15](https://developer.android.com/about/versions/15/behavior-changes-all#minimum-target-api-level) [Android 16](https://developer.android.com/about/versions/16/behavior-changes-all) [developer verification](https://developer.android.com/developer-verification)
- Path boundary: JS, TypeScript, styles, translations, and bundled assets go through EAS Update with the matching runtime; native changes such as this permission, new Kotlin, SDK or React Native upgrades, and launcher icon changes need this APK path. Do not call `Updates.reloadAsync()` while an editor or backup is active. See [docs/ota-updates-research.md](ota-updates-research.md).

## Validation gate for testing

1. Build the first binary with the permission and confirm the merged manifest contains `REQUEST_INSTALL_PACKAGES`, keeps the three `tools:node="remove"` entries, and targets API 36.
2. On the current latest build, confirm no update prompt appears; with the network off, confirm the check fails silently.
3. Fresh install, leave "Allow app installs" off, tap update, and confirm the system dialog offers the settings screen and the install completes after enabling it.
4. Interrupt a download partway, confirm no installer intent fires and a retry produces a complete file; exercise the `downloadAsync` `status` check.
5. Publish 1.1.5-15, update a device holding notes, folders, recordings, attachments, and backup history, and verify data and both manual and automatic backup still work afterward.
6. Negative tests: a build with a lower versionCode and a build signed with a different key must both be rejected by the installer with the installed app and its data untouched.
7. After the updater ships, publish a JS-only EAS Update and confirm it still applies, proving the OTA and APK paths coexist.
